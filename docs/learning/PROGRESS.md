## 已实现，待运行验收

### Lua 原子解锁

- 提交：`ee65ca2`、`2cba3c3`、`24dff02`
- 当前 Lua 脚本包含完整的 `if / else / end`。
- 当前调用只传入一个锁 key 和一个 UUID：
  `execute(UNLOCK_SCRIPT, Collections.singletonList(lockKey), uuid)`。
- 锁租约调整为 5 秒。

尚缺证据：

- `MONITOR` 中出现 `EVAL` 或 `EVALSHA`，且解锁不再由 Java 分两步执行 `GET` 和 `DEL/GETDEL`。
- 正确 UUID 能删除锁。
- 错误 UUID 不能删除锁。
- 旧租约 A 不能删除后来创建的新锁 B。

### 等待者重试与超时收尾

- 提交：`548e915`、`33b781f`、`7fce08b`
- 已改为 900ms 时间预算、单次最多等待 300ms。
- 每轮循环都会重新观察缓存和锁状态。
- 时间预算结束后会再读取一次缓存，修复了“最后一次 sleep 后直接报错”的遗漏。

尚缺证据：10～20 个并发冷缓存请求下，MyBatis 日志证明数据库查询恰好一次，并验证等待超时路径。

进阶风险：方法内 `finally` 释放 Redis 锁后，Spring 事务代理才会在方法返回后提交数据库事务。这个很短的窗口中，读请求仍可能拿到锁、查询到提交前的旧数据，并把旧数据重新写回缓存。这不否定已经完成的基础读写冲突实验，但属于下一阶段需要修正和专门验收的事务边界问题。
